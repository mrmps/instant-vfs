instant-vfs · semantic layer

One call answers "where is X?": gitvfs gets judgment from TypeSafe's Jev

Branch semantic-jev · deployed to gitvfs.miryaboy.workers.dev · 203 tests green · 15/15 bench tasks on two models

Bench: Sonnet 4.5 went from 11/15 at $0.42/task to 15/15 at $0.016/task, one tool call each

What changed

gitvfs was fast and lexical: an agent still had to guess which of /tree, /grep, /outline and /file to call, and in which order. The April traces showed that this guessing, not the data, was where calls and tokens went. Now the guessing is done server-side by a decision model.

  • /find?q=<plain question> returns ranked {path, symbol, line, endLine, probability, snippet, next} plus exists, the probability the repo contains the answer at all. When the top hit is ≥ 0.8 its source is inlined, so most questions end here.
  • /ask?q= is /find with the source always inlined; /file/<path>?about= (alias /locate) ranks lines inside one file; /grep?intent= orders matches by relevance; /verify/<path>?lines=&claim= checks an answer against the source; /tree?roles=1 tags every entry (entrypoint, core, tests, generated, …).
  • Answers are cached per (sha, question) inside the repo's Durable Object; a repeat question makes zero model calls. Every semantic response carries x-gitvfs-jev-requests / -tokens / -ms.
  • Two agent frictions found in the traces now return a suggested URL: unknown /tree params (Jev picks the param you meant), bracketed [@ref] pasted from the docs, and ?depth=1&glob=<dir>.

How /find works

flowchart TD
    Q["q: where is the body size limit enforced?"] --> P["path stage: one Choice over all paths
(beam search over directory levels when > 220 files)"]
    Q --> G["grep stage: quoted strings + code-shaped tokens
(bodyLimit, MAX_SIZE, src/foo.ts) → literal grep"]
    P --> C["≤ 255 candidates: files, outline symbols, matched lines"]
    G --> C
    C --> J["one Jev request: Choice (best location) + Noul (exists)"]
    J --> R["hits[] with probability, snippet, next URL
+ source when top ≥ 0.8"]

Code owns every step that is a lookup; the model is asked only the two questions that need judgment. Candidate sets are trimmed to the model's limits before asking, never after.

Bug found on the way (AS-010)

The first /find on facebook/react returned 502: LIKE or GLOB pattern too complex. Workers' embedded SQLite caps LIKE/GLOB patterns at ~50 bytes, and every prefix-scoped query used path LIKE 'prefix/%'. Any /tree/<deep prefix> on a repo with long paths was already a 500. Prefix scoping is now a range on the primary key, grep's prefilter uses instr(), and long user globs are evaluated in JS.

Review focus

  • src/semantic.ts — question wording and candidate construction are the product; thresholds (0.8 auto-read, 0.06 beam cutoff) are explicit constants.
  • src/repo-do.ts — the LIKE → range rewrite touches every prefix query; test/bugs.test.ts AS-010 covers tree, count, outline, grep and long globs on react.
  • Cost: a hono-sized repo is 4–5 Jev calls (~6k tokens) per new question; react is 6–9 calls (~15–37k). Cached thereafter.

Operational

  • New secret TYPESAFE_API_KEY (set). Without it the semantic routes return 503 semantic_unavailable; ?intent= and ?roles=1 degrade to the lexical result with x-gitvfs-semantic: unavailable.
  • Semantic routes share the /bash+/grep per-IP limit (30/10s) and the per-SHA throttle.
  • GITVFS_INTERNAL_KEY was rotated; the new value is in the local .env / .dev.vars (gitignored).
