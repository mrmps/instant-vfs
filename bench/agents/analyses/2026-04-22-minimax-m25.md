## Per-task behaviour

### Baseline failures

**T03 (cross-file grep) — 12 calls, FAIL.** Identical pathology to Sonnet:
```
[1] api.github.com/search/code?q=...       → 401 (unauth rate-limited)
[2] github.com/sst/opencode/search?q=...    → 200 178KB HTML
[3] github.com/sst/opencode/search?q=...    → 200 178KB HTML (retry)
[4] api.github.com/.../git/trees/?recursive → 200 1.3MB (!) full tree
[5-12] raw.github.../guessed-file.tsx       → semantic-similarity file guesses
```
Call 4 returning 1.3MB was the killer — the tree API returned the entire repo in one response, blowing the model's context budget without actually answering the question. After that the agent burned 8 calls on targeted-looking file guesses and never converged. Final answer: empty.

**T06 (symbol line number) — 1 call, FAIL.** Agent fetched `ReactHooks.js` via raw.github (7KB), then emitted an empty answer. Probably hit the 12-iteration cap while thinking-looping, or the JSON extractor missed a badly formatted answer. Minimax without numbered lines + no /outline = counting newlines by eye in a 7KB file, which it evidently couldn't do.

### gitvfs over-verification (minimax behavior)

Pattern worth calling out: **minimax distrusts tool results more than Sonnet and often pulls a file after a grep/tree has already answered.**

**T01 gitvfs — 3 calls instead of 1.**
```
[1] /grep?q=bodyLimit&files_only=1&symbols=1 → {files: ["src/middleware/body-limit/index.ts", ...]}
[2] /file/.../body-limit/index.ts?lines=1-50&numbered=1 → read 1584B
[3] /file/.../body-limit/index.ts?lines=50-100&numbered=1 → read 1957B
```
The task asked for the path. Call 1 had it. Calls 2-3 were defensive verification. Sonnet solved this in 2 calls by stopping at call 2.

**T04 gitvfs — 2 calls instead of 1.**
```
[1] /tree/packages/react/src?glob=**/*.ts&count=1 → "6"
[2] /tree/packages/react/src?glob=**/*.ts         → full list (365B)
```
Call 1 was the answer. Call 2 was "I'd better double-check by listing them." Cheap — but emblematic.

### Where minimax didn't use the best tool

**T06 gitvfs — 2 calls, should be 1.** The prompt explicitly documents `/outline` and `/symbol` for "what line does symbol X start on?" questions. Minimax ignored both:
```
[1] /file/.../ReactHooks.js?lines=1-100&numbered=1  → read file, saw line 93 by looking
[2] /grep?q=export function useState&files_only=1&symbols=1  → confirm
```
The right move was `/symbol/packages/react/src/ReactHooks.js?name=useState` → `{line: 93}`. Minimax never reached for it.

**Takeaway for AS-007/-008:** system-prompt documentation of `/symbol` isn't enough for every model. Adding a worked example ("Q: what line is useState defined on? → /symbol/packages/react/src/ReactHooks.js?name=useState") might close this gap. Or the bench itself could generate a hint: if the task mentions "line" + "function", nudge the prompt toward `/symbol`.

**T03 gitvfs — 2 calls because of `files_only=1` trap.**
```
[1] /grep?q=...&files_only=1&symbols=1  → files: [zen/index.tsx, en.ts]
[2] /grep?q=...&symbols=1                → matches: [{path:zen/index.tsx, line:238, text:..., inSymbol:null}]
```
Call 1 told minimax *which files*. Call 2 retrieved line numbers by dropping `files_only=1`. Agents default to `files_only` for "lighter" responses but then need to re-query for line info. Two real options:
1. **Smarter grep:** if `matchedFiles <= 5`, return full matches even with `files_only=1` (cheap).
2. **Prompt cue:** "If you need the line number, omit `files_only=1`."

## Where tools tied

T02, T07, T08, T09, T10: single-file reads. Both baseline (`raw.githubusercontent.com`) and gitvfs (`/file/<path>`) get the answer in one call with similar byte counts and same costs (all within $0.001 of each other).

## Modal pathology: minimax's thinking tax

T02 gitvfs is a 1-call task:
```
[1] /file/src/hono.ts?lines=1-50 → 32ms fetch, 1237 bytes
```
But the total wall-clock was **28 seconds**. The gap is all thinking tokens — minimax emitted a full `thinking` block per turn before the tool call, then again before the final answer. Output tokens for this task: 737, most of which was internal reasoning.

Cross-provider notes:
- **Anthropic Sonnet 4.5:** same task, 1 call, ~4 seconds total. Thinking tokens absent by default.
- **minimax-m2.5:** same task, 1 call, ~28 seconds total. Reasoning-native architecture.

This is not a bench bug or a gitvfs bug. It's how minimax works. For wall-clock-sensitive use cases, minimax pays in thinking time; for cost-sensitive use cases, it's wildly cheaper ($0.0015/task vs Sonnet's $0.02/task on the same workload).

## Cross-model generalization

Two different models (Sonnet 4.5 and minimax-m2.5) hit essentially identical failure patterns on the same tasks. This is the strongest signal we have so far:

1. **T03 cross-file grep is the canonical discovery task.** Both models fail it at baseline (12 calls, wrong or empty answer) and solve it in 1-2 gitvfs calls. The gap isn't model quality — it's that GitHub has no anonymous grep.
2. **T04 count is the canonical tree task.** Both models walk the GitHub tree API level by level (3-5 calls), both solve it in 1-2 gitvfs calls via `?glob=&count=1`.
3. **Single-file reads are always a tie.** Raw.github's CDN is as fast as gitvfs's DO and returns similar sizes.

The "discovery-heavy work" thesis (from CodeScaleBench) holds cleanly across models. That's a better story than any single-model number.

## Follow-up ideas surfaced by this trace

1. **Add worked examples to the gitvfs system prompt.** `/symbol` is documented but unused by minimax. Concrete before/after examples might help.
2. **Smart grep fall-through.** If `matchedFiles ≤ 5`, return matches even with `files_only=1` set — the cost is trivial and the agent avoids a second call.
3. **Auto-annotate grep: "you set files_only=1 so lines aren't in the response — drop it to get line numbers."** A one-line hint in the response could save a round-trip.
4. **`--provider anthropic` baseline re-run for apples-to-apples.** Currently we have the Sonnet run from Apr 21 on `cc762799` and the minimax run from Apr 22 also on `cc762799`. The comparison is valid but we should also run both under the new parallel harness to control for concurrency effects.
